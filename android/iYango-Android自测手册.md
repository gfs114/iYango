# iYango Android 独立自测手册

版本：1.0｜日期：2026-10-24｜适用范围：未来 Android 工程的自行安装测试。

**这是一份待执行的手册。当前没有 Android 安装包，也没有 Android 测试通过记录。** 本轮不安装工具、不连接设备、不运行下面的命令。应用商店暂不纳入验收。

主方案：[架构与开发实施方案](./iYango-Android架构与开发实施方案.md)。任务安排：[开发任务清单](./iYango-Android开发任务清单.md)。

## 1. 自测要证明什么

最少区分六类结果：业务规则正确；编译与静态检查通过；包可安装和覆盖升级；页面视觉/手势可用；学校真实请求可用；通知/日历/桌面组件在真实系统状态下可用。每项分别标记通过、失败、未验证或不适用。

例如“assembleRelease 成功”只证明构建完成，不证明锁屏通知准时；“提醒设置开关打开”不证明系统权限已授予；“小组件代码支持透明色”不证明桌面文字实际可读。

## 2. 两种测试包，分别使用

以下是建议的建项约定，包名需要在真正创建 Android 工程时固定。

| 项目 | 开发调试包 | 稳定自用测试包 |
| --- | --- | --- |
| 构建 | debug | release，暂不上传任何商店 |
| applicationId | com.gfs.iYango.dev | com.gfs.iYango |
| 名称 | iYango 开发版 | iYango |
| 签名 | 开发环境 debug 签名 | 你保管的长期 Android 签名 |
| 数据 | 虚构课表、模拟响应优先 | 日常课程；使用前备份 |
| 调试能力 | 可以启用受控测试入口与日志 | 关闭 WebView 调试和敏感网络日志 |
| 主要目的 | 定位问题、自动化、破坏性场景 | 检查 release 优化、真实提醒、覆盖升级和日常使用 |

两个包因 ID 不同可以并存，但数据库、权限、日历绑定和桌面组件配置也分别独立。**debug 数据不会自动迁入 release。** 需要迁移时使用经过验证的 JSON，不通过私自复制数据库文件实现。

稳定自用包后续必须继续使用兼容的应用签名和同一 ID。不要看到签名冲突就卸载日常包；先核对签名证书、版本和包名。应用签名密钥与上传密钥的区别见[Android 签名文档](https://developer.android.com/studio/publish/app-signing)。

建议每个安装包同时保留：文件名、版本名、versionCode、构建时间及其时区、源码版本/快照、构建类型、applicationId、SHA256、签名证书指纹、测试结果。密钥文件和密码另行安全保管，不能放进测试记录或源码仓库。

## 3. 自测环境清单

### 3.1 电脑

- Android Studio 稳定版、所选 SDK、Platform Tools 和相容 JDK。
- 项目使用自己的 Gradle Wrapper；不要使用随意安装的全局 Gradle 替代。
- 能构建离线假数据版本；测试不依赖学校网站一直在线。
- 有足够磁盘空间保存 APK、测试报告和脱敏截图。
- 网络代理、镜像、证书配置可追溯；不关闭 TLS 校验解决联网问题。

### 3.2 设备

首先选你每天实际使用的 Android 手机/平板。再补一台 AOSP/Pixel 模拟器和至少另一种厂商设备或可借用设备。只有模拟器时可以先测功能，但厂商锁屏提醒一律记为未验证。

当前鸿蒙真机如果运行 HarmonyOS NEXT，不能直接承担 Android APK 的验证。需要确认设备实际支持 Android APK，不以品牌名称代替操作系统判断。

| 维度 | 起步必须覆盖 | 扩展覆盖 |
| --- | --- | --- |
| 系统版本 | minSdk 对应模拟器、主力真机、当前目标版本模拟器 | Android 12、13、14、15、16 的权限/后台差异；可获得的更新版本 |
| 服务环境 | 不依赖 GMS 的运行环境 | 有 GMS 的设备；两者核心能力应一致 |
| 屏幕 | 手机竖屏、横屏、平板 | 分屏、小窗口、折叠屏 |
| 字体与显示 | 系统默认、较大字体 | 1.3/1.5/2.0 倍字体及显示缩放 |
| 系统导航 | 手势导航 | 三键导航、桌面窗口标题区域 |
| 主题 | 浅色、深色 | 系统自动切换、自定义壁纸 |
| 网络 | 正常、断网 | 高延迟、丢包、学校失效会话、响应结构变化 |
| 后台状态 | 前台、普通后台、锁屏 | 最近任务划掉、系统杀进程、重启、用户强行停止 |

## 5. 构建、安装与覆盖升级

下面是未来采用主方案模块结构后可使用的 PowerShell 示例。必须在新 Android 工程目录执行，**不是在 ClassSchedule-exp 中执行**。文件名与 Gradle 任务应以实际工程为准。

### 5.1 开发包

```powershell
./gradlew.bat :core:domain:test :app:testDebugUnitTest :app:lintDebug
./gradlew.bat :app:assembleDebug
adb devices
adb install -r .\app\build\outputs\apk\debug\app-debug.apk
```

首次连接时在 Android 设备上允许 USB 调试，确认序列号对应正确设备；多台设备同时连接时对每条设备命令指定 -s SERIAL。ADB 属于 Android 工具，不使用鸿蒙 hdc 来安装 APK。[ADB 官方说明](https://developer.android.com/tools/adb)

检查测试报告实际执行数量和 lint 的 issue 明细；构建命令返回 0 不一定表示没有 lint 警告或错误，项目规则需明确。单测不能运行、全部跳过或检查文件数为零时，记为没有获得有效证据。

### 5.2 稳定自用包

在 Android Studio 或受控本地配置中设置长期 release 签名，验证日志不会输出密码，然后运行：

```powershell
./gradlew.bat :app:lintRelease :app:assembleRelease
Get-FileHash -Algorithm SHA256 .\app\build\outputs\apk\release\app-release.apk
adb install -r .\app\build\outputs\apk\release\app-release.apk
```

路径是示例；实际产物必须已经签名。若输出只有 unsigned APK，不应把它当作能直接使用的稳定包。release 优化、资源收缩、混淆和调试开关要使用未来实际交付的配置测试，不能只测 debug。

### 5.3 覆盖升级顺序

1. 在旧稳定包准备 D03/D05，并添加两个不同配置的桌面组件。
2. 导出备份，确认备份可读；记录课表数、课程实例数、当前课表、主题与提醒状态。
3. 安装同 applicationId、兼容签名、较新 versionCode 的新包，使用覆盖安装方式。
4. 首次启动观察数据库迁移、缓存和状态；不出现重复课表或整库清空。
5. 核对单次调课、日历映射、通知实例、桌面组件配置与点击。
6. 断网重启应用，确认本地功能依然可用。

不要把“卸载后重装成功”当成覆盖升级通过。fresh install 测试应使用开发包或专门测试设备；不要拿有日常数据的稳定包随意清数据。

## 6. 每次改动后的 10 分钟冒烟测试

1. 启动应用，确认没有崩溃、无无限加载、未授权不自动弹一串权限。
2. 四个主入口各打开一次，返回栈正常。
3. 切换两个课表，确认没有串数据。
4. 新增一门虚构课程，编辑一次，查看今日页和周课表同步变化。
5. 首页轻下拉，圆圈清晰可见、请求完成后收起。
6. 进入后台再回来，已有数据先显示，一轮刷新完成；快速重复不会堆叠请求。
7. 离线打开，旧课表仍在，在线查询有正确的失败状态。
8. 深浅色切换、横竖屏各一次，顶部文字不压状态栏，最后一行可点击。
9. 点击一个桌面组件或通知，准确进入对应课程。
10. 有数据库/提醒改动时，加做升级或短时提醒专项；否则不能仅凭冒烟结束。

## 8. 通知提醒专项：必须实际等到触发

### 8.1 一条提醒的完整检查

1. 在开发数据中安排一门几分钟后开始的虚构课程，设置提前时间，确认最终 remindAt 仍在未来。
2. 启用应用通知，分别核对应用通知权限、通知 Channel、精确闹钟访问状态。
3. 记录预计触发时间、设备系统时间、时区和设备状态。
4. 等待触发，记录实际通知出现时间与偏差。
5. 核对课程名、教室、开始时间、锁屏隐私显示和点击目标。
6. 修改课程开始时间，确认旧提醒取消、新提醒只出现一次。
7. 停课/删课，再次确认旧提醒不会弹出。

“精确模式”可先以允许权限且无特殊限制环境下偏差不超过 60 秒作为工程自测目标，这是项目验收目标而非系统保证。若设备电源策略导致超出目标，记录实际限制并定位，不写成已通过。首版未获得精确闹钟权限时暂停应用通知提醒，并解释原因、提供授权入口或日历选择；不偷偷改用不精确提醒。如果未来另加可选降级模式，需要独立开关与延迟记录。

默认只提醒当前选中课表，提前时间 10 分钟，可改 5/10/15 分钟或关闭单门课程。切换课表后要核对旧表任务取消、新表计划建立。持久化剩余学期计划，系统闹钟接力调度最近一次提醒；同一时刻多门课逐一核对。用连续多天未打开应用的记录验证接力，不把短时单条成功当作整学期可用。

### 8.2 状态矩阵

| 场景 | 操作 | 应观察的结果 |
| --- | --- | --- |
| 前台 | 保持课程页 | 提醒按策略出现，不重复 |
| 普通后台 | 返回桌面 | 能触达；点击正确 |
| 锁屏 | 熄屏等待 | 记录实际触达时间、声音/振动和隐私内容 |
| 最近任务划掉 | 清掉应用任务卡 | 按该设备实际行为记录，不能直接等同系统强行停止 |
| 系统杀进程 | 后台模拟进程回收 | 不依赖内存列表；持久计划可恢复 |
| 设备重启 | 提醒前重启并解锁 | 重新核对计划，无重复/过期补发 |
| 时间或时区变化 | 修改后再恢复 | 采用课程约定时区，重新调度，不偏一日 |
| 权限被撤回 | 设置页关闭能力 | 状态明确；不悄悄宣称精确提醒可用 |
| 系统强行停止 | 设置中强行停止，再等待 | 记录为受限制场景；重新打开后恢复计划，不承诺停止期间触达 |
| 省电模式/Doze | 开启或模拟 | 记录实际触达与系统限流；含相隔很近的两次提醒；恢复测试环境 |

Android 的精确闹钟需要相应权限与能力检测；权限撤销会影响既有调度。[调度官方文档](https://developer.android.com/develop/background-work/services/alarms)

### 8.3 自动化和模拟边界

首先通过 FakeClock/FakeScheduler 测规则，真机再测系统触达。开发者选项“不保留活动”只能帮助观察 Activity 重建，不能代替进程死亡、Doze 或真实厂商后台测试。

如需要用 ADB 辅助 Doze 测试，应在专门测试设备上进行，并在结束后恢复。系统版本可能限制命令，失败如实记录，不改用 Root 绕过来冒充普通用户环境。可参考[Android Doze 测试说明](https://developer.android.com/training/monitoring-device-state/doze-standby)。

不要用 adb shell am force-stop 当作普通进程被系统回收的等价操作；它改变的是应用停止状态。这一差别会直接影响提醒结论。

## 9. 系统日历专项

- 先确认有可写日历；无日历时提供选择/说明，不崩溃。
- D04/D05 分别生成单双周、停课与调课事件，人工与课表对照。
- 同一计划连续同步三次，事件数量不增长。
- 修改时间/教室，只更新属于 iYango 的目标事件。
- 用户自己创建的同名事件不被删改。
- 用户删除目标日历、删除某事件或撤回权限，应用能解释并恢复。
- 模拟写入半途失败，再重试，不产生重复记录。
- 专门模拟“系统事件已插入、Room 映射尚未保存”时进程死亡：恢复后凭选定日历内唯一的非敏感归属标记接管同一事件，不新增副本。
- 删除归属标记、制造重复标记或换用不支持的 Provider：进入待确认状态，不按标题猜测后删除/重建。该恢复机制未验证前不能验收自动日历同步。
- 核对默认写入范围为剩余学期，分批失败能续作；达到容量上限时明确报错，不悄悄漏掉后半学期。
- 关闭日历通道时按事先约定处理已写入事件；清理范围可确认，不触及他人事件。
- 卸载不能被假定会自动清理已经写入系统日历的事件；提供应用内关闭/清理入口，并在测试前用专门日历隔离。
- 选择云日历时，用户知道事件可能由日历服务上传；应用不宣称完全本地。

日历 Intent 与直接 Provider 写入的能力不同，分别测试，不能拿用户点击确认的一条事件证明批量同步可用。[Calendar Provider](https://developer.android.com/identity/providers/calendar-provider)

## 10. 桌面组件专项

1. 四种组件分别添加到真实桌面，保存截图、Launcher 名称和版本。
2. 每种至少测试窄/宽两个尺寸；长名称、空课表、今天结束、明天有课都覆盖。
3. 加两个同类型组件，选择不同课表或样式，确认配置独立。
4. 编辑/同步课程后检查组件更新，记录更新时间差，不假设可秒级刷新。
5. 应用进程结束后点击组件，能冷启动正确页面；重启设备后仍能恢复。
6. 删除目标课表、停课、改时间，组件不残留可点击的错误对象。
7. 浅色、深色、复杂壁纸各测试实体、半透明、透明背景。
8. 在至少两种实际 Launcher 上验证；如只有一种，其他环境记为未验证。
9. 检查组件占用内存、图片尺寸和文本截断，避免壁纸大图塞入 RemoteViews。
10. 单独记录“已加桌”“数据正确”“跳转正常”“真实透明可读”，四项不能互相替代。

系统周期更新不是分钟级倒计时机制，组件应有主动更新与持久化状态。[组件更新说明](https://developer.android.com/develop/ui/compose/glance/glance-app-widget)

## 11. 网络、会话和故障注入

平时用 MockWebServer 或等价本地假服务制造以下响应，不在真实学校服务上批量压力测试：

- 慢请求、超时、断流、HTTP 500、返回登录 HTML 的 HTTP 200。
- 元数据成功但课程页失败；全年成绩其中一个学期失败。
- 重定向循环、跨不可信域跳转、Cookie 中途轮换。
- 教室多校区聚合部分失败、重复编码、缺失状态列。
- 账号 A 请求阻塞，切换 B 后释放 A。
- 同时触发登录、成绩刷新、课表同步，确认锁的所有者和超时处理。
- 确认导入前失败、事务中失败、事务完成后系统提醒失败，分别观察不同恢复路径。
- 写入新 planRevision 时延迟旧平台任务，确认版本检查、串行协调与补偿最终一致；注入 Room 事务回滚，确认业务和任务记录同时回滚。

真实学校验收只验证你自己的合法账号与当前功能，控制频率，不把真实账号和响应固化为测试 fixture。截图对照时遮盖个人信息。

## 12. 性能和资源检查

性能目标先作为工程目标，不伪称当前已达到：

| 项目 | 起始验收目标/方法 |
| --- | --- |
| 本地首屏 | 在主力真机上冷启动后尽快显示缓存，记录多次中位数与较慢样本；建议把 1–2 秒作为初始优化目标 |
| 滚动/切周 | 60Hz 设备以约 16.7ms、120Hz 设备以约 8.3ms 帧预算观察；使用实际工具统计卡顿，而不是只凭录屏印象 |
| 内存 | 多次切页、壁纸裁剪、开关详情与旋转后没有持续增长；记录基线和峰值 |
| 网络 | 一轮刷新可解释请求数量，无重复整学期查询和无限重试 |
| 电量 | 首页静置无周期轮询；无为课程功能维持的常驻服务；组件不高频唤醒 |
| 大数据 | 用 D14 测课程、成绩和教室列表；主线程不解析大型 HTML、不执行数据库长事务 |

先修数据错误、丢数据、崩溃和无响应，再处理微小动效。release 包的性能要单独测，debug 结果不能直接代表交付包。

## 14. 退出自测阶段的标准

### 可以自己开始日常使用

本地课表与编辑不丢数据；覆盖升级验证通过；JSON 备份可读；基本窗口和主题通过；未完成的在线/系统能力有明确状态。可以先不启用未经验证的提醒通道，但不能把它们写成已完成。

### 可以标记功能对齐

所有已承诺的功能用例通过，且至少完成一轮真实课程周的使用观察；通知和日历分别有锁屏/重启/变更的证据；四种组件有真实桌面记录；旧账号晚到结果不污染新账号；已知限制清单完整。

### 仍不能据此推断

某台手机通过不等于所有品牌通过；自行安装成功不等于符合未来应用商店审核；真实教务今天可用不等于学校接口永远稳定。尚未验证的环境保留状态，后续逐项补齐。
